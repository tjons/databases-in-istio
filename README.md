# databases-in-istio

This repo is the companion to the [Running Databases in Istio's service Mesh](https://colocatedeventsna2025.sched.com/event/28D7J/running-databases-in-istios-service-mesh-tyler-schade-michael-bolot-geico-tech) talk at Kubecon 2025.

Overall, this uses a local cluster, setup with kind, to demonstrate running two types of databases within istio - postgres (deployed through [cpng](https://cloudnative-pg.io/)) and cassandra (deployed through [k8ssandra](https://docs.k8ssandra.io/)). 

## Running the project

This project does require a few tools pre-installed, including:

- kubectl
- docker
- helm
- [kind](https://kind.sigs.k8s.io/)
- [cloud-provider-kind](https://github.com/kubernetes-sigs/cloud-provider-kind)

The make commands assume that you have a few helm repos added locally. The commands to add these projects are included here for convienence:

```bash
helm repo add jetstack https://charts.jetstack.io
helm repo add istio https://istio-release.storage.googleapis.com/charts
helm repo add k8ssandra https://helm.k8ssandra.io/stable
helm repo add cnpg https://cloudnative-pg.github.io/charts
helm repo update
```

To help demonstrate the concepts more easily, there's a makefile in the root of the project which can deploy a few resources for you. This contains the following commands:

```bash
# make setup creates a cluster, installs istio, and sets the mesh to strict security settings (MTLS required and no connections allowed by default)
make setup
# make teardown removes the cluster an any other background processes used to run it
make teardown
# make cassandra installs k8ssandra/dependencies, creates a 3 node cluster, and a client to connect to the cluster
make cassandra
# make postgres installs cnpg, creates a 3 node cluster, and a client to connect to the cluster
make postgres
```

To use the postgres client:

```bash
kubectl exec -it -n cnpg-client psql-client -- bash
# type in example-insecure from the secret manifest in cnpg/cluster.yaml
root@psql-client:/# read -s PGPASSWORD
root@psql-client:/# export PGPASSWORD
psql -U example-user -h example-pg-r.cnpg-cluster example
# you can now execute postgres queries (in read, change the hostname to "example-pg-rw.cnpg-cluster" for write)
example=>
```

To use the k8ssandra client:

```bash
# retrieve the username and password from the cassandra-creds secret
kubectl get secret -n cassandra-cluster cassandra-creds -o jsonpath='{.data.username}' | base64 -d
kubectl get secret -n cassandra-cluster cassandra-creds -o jsonpath='{.data.password}' | base64 -d
kubectl exec -it -n cassandra-client cql-client -- bash
# paste the username/password from the first steps
root@cql-client:/# read -s C_USER
root@cql-client:/# read -s PASS
root@cql-client:/# cqlsh -u $C_USER -p $PASS demo-cassandra-dc1-service.cassandra-cluster
# you can now execute cql queries
cassandra-creds@cqlsh>
```

## Manifests

There are a few concepts used accross both projects:
- Authorization Policies. We generally use these to do the following:
  - Allow the operators to talk to the clusters.
  - Allow replicas of the clusters (i.e. individual nodes/pods) to talk to one another.
  - Allow the client to talk to the cluster.
  - Allow the K8s API Server to contact the admission webhooks.
- Peer Authentication. We generally use this to allow the APIServer to contact the admission webhooks. This will cause the connection to bypass the sidecar and see the certificate generated by the pod/cert-manager, which has a SubjectAlternativeName (SAN) for the Kubernetes service hostname (unlike the sidecar cert).
